# Private events: online menu, proposals and deposits

The public entry point is `/private-events#build-menu`. Customer package choices use accessible full-card radios and a five-step package/menu/details/review/submit interface. The existing catalog controls card names, prices, counts, premium eligibility, availability and guest minimums; card presentation adds no package records or pricing constants. It explains shared buffet service, displays the configured packages and a live example, and collects a menu and event request without paperwork or payment. `/api/inquiries` saves these requests as existing `website.form_inquiries` records with `kind=event`; totals, deposit settings, venue, taxes and extra side/salad prices are recalculated on the server. The old fillable form URL redirects to the builder. `/api/private-events/menu.pdf` is an optional current menu, generated from the same configuration.

## Existing manager workflow

Use **Manager → Private Events**. Open **Website Inquiry** for incoming requests. Pending inquiry plans have yellow outlines in the calendar, event list and editor; confirmed/completed events and manually entered events use white outlines. The original inquiry record stays yellow in the archive after its event is confirmed.

The workflow is inquiry → staff planning/review → approved proposal → customer acceptance → required verified deposit → confirmed event. Merely saving a calendar draft does not confirm a date. For a manual booking, record the amount actually received under **Deposit / payments received ($)** and choose **Approve Event — No Email**. This uses the existing authorized manual-confirmation workflow, checks for overlapping bookings, retains the payment credit, and sends no customer email. No proposal or Stripe charge is required for that staff action. Each Website Inquiry has a **Delete Inquiry** button; deletion removes the original inquiry only, retaining the saved event plan, proposals and payments.

Manager-sent customer updates, proposal sends/resends and confirmation retries require explicit email approval. Changing a message or included summary clears its approval. Draft saving, editing and kitchen printing send no email. The same explicit approval applies to manual tour messages/cancellation notifications and customer campaigns; manually adding a tour guest sends no customer email unless the notification checkbox is approved. Automatic customer-initiated inquiry acknowledgments and verified-payment confirmations retain their existing workflow.

Use the existing controls as follows:

1. Open **Website inquiries — start an event plan** and choose **Plan event**. The saved package, food selections, dates, contact details and special requests populate the existing editor. A linked inquiry reopens its existing event instead of making a duplicate.
2. Review the menu, guest count, charges and requested date. Save the event. Its main status remains one of the existing Draft / Tentative / Confirmed / Completed / Cancelled values. The additional inquiry/proposal/payment label describes its booking progress.
3. In **Customer proposals & deposit payments**, choose an expiration and create a proposal draft. Preview, download or print its PDF. Creating and printing a draft do not send email.
4. Check the calendar and venue capacity, then use **Approve & send proposal**. The server checks overlapping tentative/confirmed events, including the established one-hour setup and 30-minute removal windows. Approval holds the existing event as Tentative. The customer receives a secure link and optional attached PDF; the link can be resent. Resending replaces the previous access link.
5. Customer acceptance records the proposal version, policy version, name, timestamp, user agent and a hash of the request IP. Payment uses the existing Stripe Checkout integration. No card details are collected by this application.
6. Only a verified Stripe payment notification records a deposit. Session and Payment Intent uniqueness prevent duplicate payment records and credits. Confirmation requires approved, unchanged event terms, a matching payment and a final availability check. Changed, cancelled, expired or conflicting terms leave a recorded payment for staff review instead of falsely confirming a booking. Confirmation delivery failures remain retryable without repeating the payment credit.
7. Refresh acceptance/payment status in the manager. Download a deposit receipt or open **Kitchen Production Sheet / Print**. Authenticated staff can preview and print kitchen sheets for any saved event without sending a proposal first. Unapproved draft/tentative events are clearly marked “DRAFT — NOT APPROVED FOR PRODUCTION”; approved proposals, confirmed events, completed reference copies and canceled events each carry their own status label. Printing never approves or confirms an event. It includes selected food, desserts/coffee, custom food rows and dietary/production notes. It excludes billing amounts, payment references, customer email/phone and general administrative notes. No yield data exists, so it does not invent production quantities or pan counts.

Use the existing event status and guest-update controls to complete or cancel events, apply existing authorized manual booking exceptions, or send additional updates. Cancelling a plan never deletes payment history. Moving a previously approved plan back to Draft revokes its proposal approval; a late payment cannot confirm it. Declined or expired proposals are shown for review; staff can release a remaining tentative hold through the existing event status control.

When an event already has the required deposit recorded (manual or verified Stripe credit), the proposal email offers **Review & Approve Proposal** and **Request a Change**. The secure review page shows the existing credit and an **Approve Proposal — Deposit Already Paid** button. Approval still records the exact proposal/policy version, customer name and timestamp and checks availability; it creates no additional deposit checkout when the credit covers the requirement.

**Request a Change** opens an online message form under the same expiring secure link. Requests are stored against that exact proposal version, displayed in its manager proposal box with the customer name/time and events-team email status, and sent to `events@aviatorbrew.com` through the existing delivery queue. Duplicate submissions do not duplicate the record or notification. The saved event/menu, payment credit and historical acceptance are retained. A proposal with requested changes requires a revised draft before another acceptance or send; a late payment remains credited for staff review. Staff can retry failed notifications using the existing approved delivery controls. Previously sent/accepted proposals and their request history remain available after revision.

Each proposal card has a **Proposal status** label: Draft, Approved — Not Sent, Sent, Customer Accepted, Manual Accepted, Changes Requested, Declined, Cancelled, Superseded or Expired. Acceptance and payment are shown separately. Accepted historical proposals retain their acceptance label after the response deadline.

Use **Manual Customer Accepted** on the latest saved proposal to record acceptance received by phone, in person or outside the website. Confirm the customer name and optionally add a staff-only note. The existing acceptance audit records the method, exact proposal/policy version, name, recording timestamp and manager-portal source. It sends no email, changes no payment credit and does not automatically approve the date or confirm the booking. The existing **Approve Event — No Email** workflow remains available for authorized booking confirmation. Stale, expired, closed or changed proposals require a new draft, and an existing customer or manual acceptance cannot be overwritten. Staff notes are visible in the manager only; customer pages and PDFs identify manual acceptance without exposing those notes.

For a business meeting or event without buffet catering, choose **No food — meeting only**, **Meeting & drinks — no food**, or **Custom / off-menu food & drinks** under **Food & beverage plan**. Event type (including General business meeting) and company/organization are visible above that selector. Keep the normal contact, date, start/end time, guest count, location, setup, bar and AV details. Describe room layout, drinks and off-menu requests in **Meeting, drinks & off-menu notes** or the existing event notes. Add only agreed custom charges under **Order summary & custom charges**; notes and service-plan choices add no automatic package charge. The buffet selection counts and guest minimum apply when a buffet package is chosen; venue capacity and availability checks remain in place. Summaries and proposals identify the custom service plan and do not claim that buffet service or beverages are included. Existing plans/issued quotes retain their stored details.

## Settings and activation dependency

Extend the existing **Website settings & room booking fee** panel; there is no separate catering administration application. It now contains package names/prices/selection limits, premium eligibility, food choices/availability, upgrade prices, venue minimum/maximum and taxes. Disable dishes instead of deleting names used by saved events. Existing event data and legacy menu selections remain stored.

**Approved cancellation, deposit/refund, and final guest-count policy text is not configured in the existing system.** No business terms were invented. Add the approved complete text and a policy version in **Customer acceptance policies**, then create a new proposal. Changing policy text requires a new version. Drafts created without policies cannot be sent, accepted or paid. Stripe Checkout, the signed webhook secret, and email delivery must also be configured before a payment proposal can be sent.

The current configured Ready Room deposit is $350; it is loaded from existing settings, quoted in each proposal, and credited toward the event total. Recorded payments reduce any further deposit due. Neither a customer-supplied total nor a payment-return URL can mark an event paid or confirmed. Bar consumption, gratuity and unpriced services are explicitly excluded unless staff itemizes them.

## Revisions, availability and access

Issued proposals keep an immutable snapshot of menu selections, charges, taxes, deposit requirements and policy text/version. Configuration updates do not alter those snapshots. Material event changes invalidate the old acceptance for the changed terms. Create and send a revised proposal and obtain new acceptance. Existing payment credits carry forward; they are not charged again. Manual payment edits cannot remove verified Stripe credits, and recording a manual deposit closes an older unpaid checkout before a second payment can be taken. Before another version becomes payable, the app verifies and closes an older unpaid Stripe checkout. An unresolved or already-paid attempt blocks a second payment link until reconciled.

Customer links contain a random 256-bit bearer token in the URL fragment; only its hash is stored on the server. The browser removes the fragment and keeps the token in session storage to resume after Stripe checkout. Tokens never enter page request URLs or analytics events. Customer API responses and PDFs are private/no-store, and the review page is noindex with no-referrer. Invalid, superseded or expired links cannot authorize payment. Staff retains authenticated access to historical proposals and receipts after customer links expire.

Event plan writes and booking checks share a PostgreSQL advisory lock to serialize availability changes. Existing tentative/confirmed records remain authoritative; both the saved window and a changed Google source window block conflicting bookings until staff resolves the difference. imported Google bookings and manager-entered data are preserved. Only the Ready Room venue and capacity rules currently configured in this application are offered publicly. Larger/outdoor arrangements require staff review; no extra capacity or production yields were invented.

## Database and integration

Schema changes are additive and included in both existing migration paths. New related tables are `private_event_proposals`, `private_event_checkout_attempts`, `private_event_deposits`, `private_event_deliveries`, and `private_event_proposal_changes`. Existing inquiry, event, tour, shop and payment records are not rewritten by the migration. No BrewOps integration or additional Render service is used.

Stripe events are handled by the existing `/api/stripe/webhook` endpoint. It verifies the raw request signature, including timestamp tolerance and rotated signatures. The proposal branch supports Checkout completion, asynchronous success/failure and expiry; card Checkout is used for deposits. Stripe idempotency keys preserve a single checkout across retries. The existing shop and tour branches are retained.

## Validation

`npm run test:event-booking` requires a fresh, isolated local PostgreSQL database:

```
EVENT_TEST_DATABASE_URL=postgres://test_user@127.0.0.1:5432/aviator_event_test_example npm run test:event-booking
```

The script refuses nonlocal databases and database names outside `aviator_event_test_*`. It uses actual schema migrations/services, simulated Stripe responses and a stub mail transport. It tests pricing, limits, disabled items, tampering, inquiries, immutable quotes, policy gates, acceptance metadata, concurrent/idempotent checkout, signed webhooks, duplicate notifications, email retry, deposit credits, PDF output, kitchen privacy, material revisions, conflicts, expired/failed/cancelled payments, and closing an older unpaid checkout. No real charge or external email is sent.

Manager email-route regression: `node scripts/test-manager-email-approval.mjs` exercises blocked and approved paths with stub mail, data and authentication services; it makes no external requests or database writes.

Related regressions: `npm run test:event-plans`, `npm run test:calendar-sync`, and `npm run test:tours`. Browser verification uses the same disposable local database, including real inquiry-to-event import, optional menu PDF, proposal review/acceptance, receipts, manager authorization and mobile layouts. Payment return parameters are tested independently of verified payment state.
