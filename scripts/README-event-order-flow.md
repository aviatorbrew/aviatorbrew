# Private Events office workflow

The main event heading stays visible, with **MENU**, **Event Order Flow**, **Event Actions** and **Print orders & receipts** collapsed below it by default. Each has a thicker outline and an arrow control (left arrow when open). Expanding or collapsing a section keeps its fields mounted and preserves unsaved edits. Saving invalid fields and the missing-details shortcut reopen the menu so the field can be corrected. The closed flow row still displays the saved booking and customer-response status. Save, direct staff approval, customer updates, cancellation, deletion, proposal drafting, acceptance and deposit reminders use their existing handlers, approval gates and confirmation prompts. Nothing advances automatically just because the flow is displayed.

Milestones come from the saved plan, latest proposal version, acceptance records and verified payment ledger. Customer acceptance, booking confirmation and deposit payment remain independent. A manually confirmed event can skip proposal milestones, while still showing an unpaid deposit. A revised proposal needs its own acceptance; earlier payments remain credited. An open/creating checkout or a paid provider attempt awaiting its ledger entry is pending, not a recorded payment. Existing saved payments and verified Stripe payments are not double counted.

The flow history uses recorded timestamps only. The latest proposal remains open. Previous proposals, including superseded versions and earlier paid records, are collapsed into one history row by default. Expanding it shows compact version rows with their original customer responses and payment records. Earlier PDFs and receipts are separately collapsed in Print orders & receipts. A customer status line identifies whether the latest version is unsent, awaiting acceptance, accepted online/manually, changed, or expired; booking confirmation and deposits do not imply acceptance of a revised quote. No confirmation timestamp is invented where the current event model has none. Manual payments are identified without inventing a receipt time.

**Print orders & receipts** is separate from actions and includes kitchen sheets, summaries, menu planning sheets, proposal previews/downloads and available deposit receipts. Printing and saving do not send customer emails. Staff must still approve customer email delivery and confirm its recipient.

Validate with `npm run test:event-plans`, the production build, and desktop/mobile manager browser checks using mocked records/providers. Do not issue real customer emails, payments or event mutations for automated testing.

Calendar selections, list Edit buttons and existing-event links expand the saved event directly inside its matching list row. Only one editor is mounted. Selecting the same event again focuses its open editor without reloading unsaved fields. Selected events outside the current search/date filter remain visible while editing, then return to the normal filtered view on close. New, unsaved plans use the new-event editor until saved to the list. Opening a calendar entry only reads the existing event; it does not create a booking.

The event title, status, date, start/end times, food-out time, contact and estimate remain visible above the editing sections. The title arrow toggles the event; calendar reselection only focuses it. Imported/manual events also show a read-only list of website menu submissions for the exact event date, with the original submitted menu and a shortcut that expands the matching Website Inquiry. Same-date submissions are candidates for staff review, not automatic merges or approvals. Opening either view does not mark an inquiry reviewed or send email.

Menu and proposal children have distinct, event-specific React keys so saved-plan/proposal refreshes cannot reconcile one section as the other. Browser checks must fail on duplicate-key console errors and assert exactly one Menu/form after editing and refreshing, not only on initial load.

`npm run test:event-editor-ui` runs the browser regression against the prepared standalone build, using only mocked manager APIs. It requires Playwright to be available (or set `AVIATOR_PLAYWRIGHT_MODULE` to its installed module path). `EVENT_EDITOR_UI_ORIGIN` can point to deployed assets; manager reads and writes remain intercepted. The fixture reproduces an imported booking with no food and a separate submitted menu, and checks editing, saving, refreshes, inquiry navigation, persistent headings, duplicate sections/React-key errors and mobile layout.
